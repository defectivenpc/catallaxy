# RFC 0005 — Labs: clusters, containment, and environments

Status: **Draft**, amended Scope: how floes are assembled into something
deployable. Depends on RFC 0001.

> **Amended.** §1–§4 originally made the lab and the cluster floes as well,
> so that one mechanism served every depth. The implementation went the
> other way; §1.1 gives the reason and §2.1, §3.1 and §3.2 name what that
> costs. The examples in those sections are now the shipped tree rather than
> a sketch. §5–§8 are unchanged except where they asserted something §1–§4
> no longer claims.

RFCs 0001–0004 define what a floe is and what it delivers. None of them
shows one being _used_. This RFC defines what contains a floe, and is mostly
worked examples — a cluster, a lab, and the same lab as several
environments.

A cluster is a Kubernetes concept, so this document is domain-specific by
nature, as RFCs 0002–0004 are. What it demonstrates — containment,
instantiation, environments, allocation — is not: a domain with different
delivery categories (RFC 0001 §6.4) assembles its components the same way.

## 1. A lab is a module. A cluster is a set of floes.

Containment is at three depths, but only the innermost one is the floe
mechanism:

```text
environment  is a module merged over  a lab module
lab module   holds                    clusters and appliances
cluster      holds                    component floes, linked as one unit
```

A **cluster** is `lab.clusters.<name>`: a set of instantiated floes, linked
together and elaborated into a wave plan. One of its members is a
provisioner floe that provides `KUBERNETES_CLUSTER` and emits the descriptor
the cluster is created from — so the provisioner is an ordinary floe even
though the cluster containing it is not.

A **lab** is a NixOS module holding clusters and the appliances that serve
them.

An **environment** is a second module merged over the lab's.
`examples/labs/<lab>/lab.nix` crossed with `<lab>/envs/*.nix` gives
`<lab>.<env>`, and the lab file is first in the module list — so anything it
writes with `mkDefault` is what an environment may change.

### 1.1 Why the asymmetry

An earlier draft of this RFC made the lab and the cluster floes as well, on
the grounds that one mechanism at every depth beats three. The
implementation went the other way, and the reason is stated at
`modules/lab/types.nix:1-8`:

> A lab is a NixOS module, not a floe. Floes are the inter-component
> interface, which the module system is bad at; a lab is partial
> configuration merged from several files, which is what it is good at.

That argument cuts both ways, which is why it settles the question.
_Between_ components you want hiding, named interfaces, exactly-one
resolution and blame — everything a single global option tree with
merge-everything semantics denies you, and the denial is why RFC 0001 exists
at all. _Within_ a lab you want precisely that global tree: `envs/tls.nix`
overriding `lab.proxy.httpPort` and adding three floes to a cluster the base
file already declared is a merge, and expressing it as instantiation would
mean threading every one of those through a settings record.

The cost is real and is not hidden by saying it this way. An appliance is
not a floe, so `lab.dns` is an option surface rather than a signature.

`lab.provides` closes the half of the gap that mattered: the option surface
stays the merge target, and the lab builds a floe instance out of the merged
result, which every cluster then resolves through an ordinary signature
(§3.1). The wiring between a lab fact and the floe reading it is typed
again; what is still a plain option tree is the _authoring_ of that fact,
which is exactly where the merge argument above says it belongs. RFC 0004
would go further and is not built.

## 2. A cluster, written out

```nix
# examples/labs/minimal/lab.nix, in part
lab.clusters.app.floes = {
  cluster = floes.k3d-cluster {
    name          = "app";
    instanceName  = "minimal-local-app";
    podSubnet     = "10.244.0.0/16";
    serviceSubnet = "10.96.0.0/12";
  };

  gateway-api  = floes.gateway-api-crds { manifest = "${k8sSpecs.standaloneCrds.gateway-api}"; version = "v1.2.1"; };
  cert-manager = floes.cert-manager     { chart = "${cataCharts.cert-manager.chart}"; };
  gateway      = floes.gateway          { chart = "${cataCharts.traefik.chart}"; baseDomain = config.lab.dns.zone; };
  podinfo      = floes.podinfo          { };
};
```

That is the whole of what a cluster is: an attrset of instantiated floes.
Nothing declares an ordering, because nothing may — the linker resolves the
signatures and the elaborator derives the install order from them (RFC 0002
§5).

Three things to notice.

**The provisioner is not a closed set.**
`floes/provisioners/k3d-cluster.nix` is an ordinary floe: inputs, one
`provides` (`KUBERNETES_CLUSTER`), one output kind (`catallaxy.cluster`). A
Talos cluster, a managed cloud cluster, or one that already exists is
another floe providing the same signature, and every member is unchanged by
the choice. A cluster that already exists provides the signature and emits
no descriptor — RFC 0004 §6's "providing without running", one level up.

**A member reads cluster facts through the signature**, not from an ambient
namespace. `requires.cluster = sigs.KUBERNETES_CLUSTER` gives a floe the
name, version, context and ranges, so a floe that touches a cluster fact has
said which. There is no cluster namespace to read instead.

**Those facts are inputs, not deferred outputs.** You choose a service CIDR;
you do not discover it. This matters — see §6.3.

### 2.1 What creates the cluster, and what does not

The floe emits a descriptor, and the lab lowers it to a `create-cluster`
step in the same plan as everything else
(`modules/lab/planner/kinds/create-cluster.nix`).

RFC 0003 describes this differently: the cluster's existence should be a
`resources` declaration on the floe, driven by a state-based tool, and the
descriptor above should not need to exist. That category is not built. The
field names of `catallaxy.cluster` track `ClusterSpec` in
`cli/src/domain/cluster.rs` for that reason — when `resources` arrives,
moving to it is a lowering rather than a translation.

## 3. A lab, written out

Two clusters, the appliances that serve both, and one component in each
cluster.

```nix
# examples/labs/homelab/lab.nix — merged with one of envs/*.nix
{ lib, cataCharts, floes, config, ... }:

{
  lab.name     = lib.mkDefault "homelab";
  lab.dns.zone = lib.mkDefault "homelab.test";

  # The appliances, serving the whole lab. Options, not floes — see §1.1.
  lab.dns.enable      = true;
  lab.proxy.enable    = true;
  lab.registry.enable = true;

  lab.clusters.core.floes = {
    cluster = floes.k3d-cluster { name = "core"; instanceName = "homelab-core"; };

    gateway = floes.gateway {
      chart      = "${cataCharts.traefik.chart}";
      baseDomain = config.lab.dns.zone;
    };

    harbor = floes.harbor { chart = "${cataCharts.harbor.chart}"; };
  };

  lab.clusters.mgmt.floes = {
    cluster = floes.k3d-cluster {
      name          = "mgmt";
      instanceName  = "homelab-mgmt";
      podSubnet     = "10.245.0.0/16";
      serviceSubnet = "10.112.0.0/12";
    };

    gateway = floes.gateway {
      chart      = "${cataCharts.traefik.chart}";
      baseDomain = config.lab.dns.zone;
    };

    forgejo = floes.forgejo { chart = "${cataCharts.forgejo.chart}"; };
  };
}
```

What this shows, and what each part of RFC 0001 is doing here:

| In the example                          | Mechanism                                                            |
| --------------------------------------- | -------------------------------------------------------------------- |
| `floes.gateway { … }` appears twice     | two instantiations, two identities (RFC 0001 §7.1) — nothing renamed |
| `harbor` requires `API_GATEWAY`         | resolves to `core`'s gateway; a link is per-cluster                  |
| `harbor` requires `X509_ISSUANCE`       | **link error** naming both: nothing in `core` provides it            |
| `config.lab.dns.zone` reaches `gateway` | read off the lab's options, passed at instantiation                  |

`harbor` never names `core`, never names the gateway implementation, and
never spells a hostname belonging to anything else. That much the design
delivers.

### 3.1 A link is per-cluster, and the lab is its scope

`modules/lab/cluster.nix` calls `link` once per cluster, over that cluster's
floes plus a **scope**: the provides the lab offers it. Resolution is
nearer-first — a hole is filled by a unit of this link if one provides the
signature, and only otherwise from the scope. A cluster with its own gateway
keeps it; one without picks up whatever the lab offers.

The scope has two sources, and they are the two directions of §3.2:

```text
labLink   = link { units = lab.provides }              # no scope of its own
scope(X)  = labLink.provides
          ∪ ⋃ { Y's offered provides | Y ≠ X }
cluster X = link { units = X.floes; scope = scope(X) }
```

Two properties are enforced by that shape rather than by a rule:

- **The lab's own provides cannot depend on any cluster.** `labLink` is
  given no scope, so §6.2's stratification holds by construction.
- **A cluster's own offers are excluded from its own scope.** Otherwise a
  cluster that both offers and consumes would depend on its own link result
  — an evaluation cycle, not a resolution ambiguity.

Exactly-one still holds within each tier, and across the whole lab: two
clusters offering one signature is refused at the lab
(`nix/checks/lab-scope.nix`), once, rather than N−1 times as each other
cluster fails to choose.

A fact the lab holds reaches a floe through a floe. `lab.provides` takes
floe instances that install nothing — there is no cluster for them to render
into — and exist to answer a signature. `floes/lab/zone.nix` is the first:
`lab.dns.*` stays the authoring surface an environment writes, the lab
builds one `lab-zone` out of the merged result, and `lab-dns`,
`external-dns` and `gateway` require `DNS_ZONE` instead of taking a zone, a
server and a port as hand-passed inputs.

That last is the price §1.1 named, now partly paid. It was six arguments
across two floes with nothing checking they agreed, and they did not:
`every-floe` pointed external-dns at port 53 while the lab's own server
listened on 5354.

### 3.2 What crosses between clusters, and what does not

**Secrets do.** A cluster publishes a Secret into a runtime store and
another subscribes to it under a name of its own choosing
(`lab.clusters.<c>.secrets.{publish,subscribe}`).
`examples/labs/tests/secret-sharing.nix` pins the whole chain: an authored
store holds the runtime store's credential, each cluster projects it in, one
cluster mints a CA and publishes, the other subscribes. Neither cluster
reads the other's configuration, so nothing can cycle.

**Configuration does, per field.** `lab.clusters.<c>.provides` names units
whose provides are offered up to the lab, and every other cluster resolves
against them when nothing of its own answers first. The lab author writes
that list, which is where §5 says an address plan belongs — a cluster does
not decide unilaterally to be depended on.

What crosses is decided per _field_, by `T.local` (RFC 0001). A provide
arriving from another link has every local field replaced by a throw naming
the field and where it came from, so reading one is an error and not reading
one is fine. A signature whose fields are _all_ local — `X509_WEBHOOK`, a
webhook serving admission for CRDs installed here — is refused as a scope
entry up front, rather than at whichever field a consumer touched first.

The granularity is the point. `MESH_NETWORK` carries both a public
management URL and a cluster-internal one; the first crosses and the second
cannot, and no per-signature flag reaches that.

## 4. Environments

An environment is a file under `envs/`, merged over the lab's own module.

```nix
# examples/labs/minimal/lab.nix — what every environment shares
{ lib, ... }:
{
  lab.name     = lib.mkDefault "minimal";
  lab.dns.zone = lib.mkDefault "minimal.test";

  lab.clusters.app.floes = { /* … as in §2 … */ };
}

# envs/local.nix — plain HTTP, no ingress
{ ... }:
{
  lab.name              = "minimal.local";
  lab.network.subnet    = "172.20.0.0/16";
}

# envs/tls.nix — the same lab, serving https from a CA it mints
{ lib, cataCharts, floes, config, ... }:
{
  lab.name           = "minimal.tls";
  lab.network.subnet = "172.25.0.0/16";
  lab.proxy.enable   = true;
  lab.proxy.httpsPort = 8443;      # local already claims 443

  lab.clusters.app.floes = {
    # present only here
    trust-manager = floes.trust-manager { chart = "${cataCharts.trust-manager.chart}"; };

    # replacing one the base file declared
    gateway = lib.mkForce (floes.gateway {
      chart      = "${cataCharts.traefik.chart}";
      baseDomain = config.lab.dns.zone;
      tlsEnable  = true;
    });
  };
}
```

Four environments of one lab in the shipped tree. What varies is what an
option can carry, plus which floes are present.

**There is no `enable`.** A floe absent from `lab.clusters.<c>.floes` is
simply not instantiated there. If something required what it provided, that
is a link error naming both — and it should be, because omitting a
certificate issuer really does break everything needing certificates. A floe
that genuinely tolerates absence declares the hole `requiresOptional` and
handles the null.

**Adding is a merge; replacing is `mkForce`.** A floe instance is an opaque
value, so the module system has no merge for two of them — an environment
that wants different inputs to a floe the base file already declared states
that, rather than getting a silent last-one-wins.

**Environments have distinct identities**, which is what keeps their state
apart: each sets its own `lab.name`, its own subnet and its own host ports,
so two of them run side by side on one docker host. RFC 0003 §5 keys a stack
the same way, for the same reason.

## 5. Allocation

Subnets, host ports and pinned addresses are scarce resources shared across
a lab. They are **not** resolved by linking. An address plan is a decision,
so it is written where the lab is declared — visible in §3 above, as literal
values on each cluster.

A lab-level check refuses:

- two clusters whose pod or service ranges overlap
- two clusters whose ranges overlap the host network's
- a pinned address outside the range it claims to be in
- two appliances on one host port

Two alternatives are worth refusing explicitly. Making the allocator a
provider whose value differs per consumer would reintroduce the one shape
RFC 0001 §8.1 rules out. Deriving each range from a cluster's own name needs
no coordination at all — and renaming a cluster would then silently move a
running cluster's subnet, which is the instability that ruled out
graph-derived state identity in RFC 0003 §5. A decision written down and
verified beats a derivation that is wrong under rename.

## 6. Why this terminates

Containment plus linking could in principle chase its own tail. Three rules
stop it, and they are obligations on any implementation.

### 6.1 Containment is acyclic

A floe may not contain itself, directly or transitively. The type is
recursive — a floe holds floes, as a directory holds directories — but the
instance graph is a finite tree.

This rule is currently vacuous and is kept because the obligation outlives
the implementation: no floe contains another today, since the two containing
depths are the lab module and the cluster attrset (§1). The rule binds the
moment a floe may hold floes.

This is where the borrowed model's own limit is informative. Backpack
composes units freely but **forbids cyclic unit dependencies**; there are no
recursive modules. MixML does permit recursive linking and is markedly more
complex for it. Forbidding cycles is not a simplification we are inventing.

### 6.2 A container's provisions may not depend on its contents

Evaluation is stratified, and the strata are what make the fixpoint
converge:

```text
1. a container's settings and provisions      (from its own configuration)
2. its contents' evaluation                    (may read 1)
3. the container's aggregate delivery          (folds 2)
```

A cluster's `kubernetes-cluster` values come from its own settings. Its
members read them. Its total delivery is its own resources plus its members'
bundles. Three layers, no cycle.

Inverting stratum 1 — a cluster whose version is "whatever my members need"
— is a genuine cycle with no fixpoint, and must be refused rather than
diagnosed by timeout.

### 6.3 Cluster facts a manifest needs are settings, not deferred outputs

RFC 0003 §4 forbids a deferred value from reaching a manifest: a manifest is
rendered at build time and there is nothing to interpolate.

A cluster's members render manifests, so every cluster fact they read has to
be known before apply. In practice this is how it already works — you choose
the pod CIDR and the service CIDR, you do not discover them.

Facts that genuinely are discovered, such as an assigned API endpoint, are
deferred and reach a workload the way any deferred value does: through
publication (RFC 0003 §7), as a handle to a materialised object.

## 7. Open questions

1. **Cross-cluster ordering.** A component in one cluster provisioning
   another is an ordinary requirement, so the link graph knows the edge.
   Whether that edge should also constrain the _apply_ order across clusters
   — rather than being satisfied by the second cluster simply not existing
   yet — is undecided.
2. **What a container may read of its contents.** §6.2 forbids provisions
   depending on contents. Derived aggregates over contents (RFC 0001 §8,
   third flow) are stratum 3 and legitimate. The exact boundary is stated
   here as a rule and not yet as a check.
3. **Sibling containers.** Answered (§3.1, §3.2). A cluster offers units
   upward, the lab offers its own provides downward, and every cluster
   resolves against the union with nearer-first. Portability is per field
   (`T.local`).

   What remains open is _depth_. The scope is one level: a lab, and its
   clusters. Nothing composes a lab into something larger, and the same
   argument that produced this scope would produce the next one.

4. **Where definitions come from.** The shipped set is an attrset of paths
   in `floes/default.nix`, applied by `lib/lab.nix` so a lab writes
   `floes.harbor { … }`. Whether floes are distributed, versioned and
   resolved by something more than a path is left to whatever ships them.

## 8. How to evaluate this concept alone

1. A cluster is declared with a provisioner, a version and its ranges, and
   the provisioner is not a special case of the floe model.
2. Swapping k3d for a managed cluster changes one instantiation, and no
   member.
3. The same component appears in two clusters with no renaming anywhere.
4. A shared appliance is configured once and serves every cluster.
5. A component requiring something nothing provides is a link error naming
   both, not a silent null.
6. Several environments differ by settings and by which members exist, from
   one definition.
7. Two environments' state does not collide.
8. An address plan is written down once and a check refuses an overlap.
9. A cluster whose facts depend on its members is refused, not timed out.
