# RFC 0005 — Labs: clusters, containment, and environments

Status: **Draft** Scope: how floes are assembled into something deployable.
Depends on RFC 0001.

RFCs 0001–0004 define what a floe is and what it delivers. None of them
shows one being _used_. This RFC defines what contains a floe, and is mostly
worked examples — a cluster, a lab, and the same lab as three environments.

A cluster is a Kubernetes concept, so this document is domain-specific by
nature, as RFCs 0002–0004 are. What it demonstrates — containment,
instantiation, environments, allocation — is not: a domain with different
delivery categories (RFC 0001 §6.4) assembles its components the same way.

## 1. A lab is a floe. So is a cluster.

There is no separate lab type, cluster type, or environment mechanism. All
three are the containment declaration from RFC 0001 §6 at different depths:

```text
environment  instantiates  a lab floe
lab floe     contains      cluster floes and appliance floes
cluster floe contains      component floes
```

A **cluster** is a floe that provides `kubernetes-cluster`, brings itself
into existence through its `resources`, and contains its members.

A **lab** is a floe whose members are clusters and appliances, and whose
settings are what an environment fills.

An **environment** is an instantiation of a lab floe. Dev, staging and
production are three instantiations, with three identities, from one
definition.

## 2. A cluster, written out

```nix
# k3d-cluster.nix — a definition, instantiated once per cluster
{ config, k8s, ... }:

{
  settings = {
    name          = t.str;
    version       = t.str.default "1.31";
    podSubnet     = t.cidr;
    serviceSubnet = t.cidr;
  };

  provides.kubernetes-cluster = {
    implements = "1";
    version    = config.version;

    values = {
      inherit (config) name version podSubnet serviceSubnet;
      context = "k3d-${config.name}";
    };

    backedBy = [ config.resources.cluster ];
  };

  resources.cluster = {
    provider = "k3d";
    type     = "k3d_cluster";
    phase    = "before-clusters";
    inputs   = {
      name           = config.name;
      k3s_version    = config.version;
      cluster_cidr   = config.podSubnet;
      service_cidr   = config.serviceSubnet;
    };
    outputs = [ "kubeconfig" ];
  };
}
```

Three things to notice.

**The provisioner is not a closed set.** This is an ordinary floe. A Talos
cluster, a managed cloud cluster, or a cluster that already exists is
another floe providing the same signature, and every member is unchanged by
the choice. A cluster that already exists provides `kubernetes-cluster` and
declares no `resources` at all — RFC 0004 §6's "providing without running",
one level up.

**A member reads cluster facts through the signature**, not from an ambient
namespace. `uses.kubernetes-cluster.values.serviceSubnet` is a declared
requirement like any other, so a floe that touches a cluster fact has said
which.

**Those facts are settings, not deferred outputs.** You choose a service
CIDR; you do not discover it. This matters — see §6.

## 3. A lab, written out

Two clusters, one shared appliance, one component in each cluster requiring
it.

```nix
# homelab.nix — a definition, instantiated once per environment
{ config, ... }:

let
  k3dCluster = import ./k3d-cluster.nix;
  localDns   = import ./local-dns.nix;
  gateway    = import ./gateway.nix;
  harbor     = import ./harbor.nix;
  forgejo    = import ./forgejo.nix;
in
{
  settings = {
    domain   = t.str;
    replicas = t.int.default 1;
  };

  # An appliance, instantiated once for the whole lab (RFC 0004).
  floes.dns = localDns {
    zone = config.domain;
  };

  floes.app = k3dCluster {
    name          = "app";
    podSubnet     = "10.244.0.0/16";
    serviceSubnet = "10.96.0.0/12";

    floes = {
      gateway = gateway { };

      harbor = harbor {
        domain   = "registry.${config.domain}";
        replicas = config.replicas;
      };
    };
  };

  floes.mgmt = k3dCluster {
    name          = "mgmt";
    podSubnet     = "10.245.0.0/16";
    serviceSubnet = "10.112.0.0/12";

    floes = {
      gateway = gateway { };
      forgejo = forgejo { domain = "git.${config.domain}"; };
    };
  };
}
```

What this shows, and what each part of RFC 0001 is doing here:

| In the example                                        | Mechanism                                                            |
| ----------------------------------------------------- | -------------------------------------------------------------------- |
| `gateway { }` appears twice                           | two instantiations, two identities (RFC 0001 §7.1) — nothing renamed |
| `harbor` requires `dns-zone`, provided by `floes.dns` | outer instances are candidates for inner ones (RFC 0001 §7.1)        |
| `harbor` requires `api-gateway`                       | resolves to `app`'s gateway, not `mgmt`'s — nearer wins              |
| `harbor` requires `certificate-issuance`              | **link error**: nothing in this lab provides it                      |
| `config.domain` reaches `harbor`                      | a setting passed at instantiation (RFC 0001 §6.1)                    |

That last row is the point of the design. `harbor` never names `app`, never
names the DNS implementation, and never spells a hostname belonging to
anything else.

## 4. Environments

```nix
let homelab = import ./homelab.nix; in
{
  environments.dev = homelab {
    domain = "dev.lab.test";
  };

  environments.staging = homelab {
    domain   = "staging.example.com";
    replicas = 2;
  };

  environments.prod = homelab {
    domain   = "example.com";
    replicas = 3;

    # present only here
    floes.app.floes.velero = velero { schedule = "0 2 * * *"; };
  };
}
```

Three instantiations of one definition. What varies is what a setting can
carry, plus which members are present.

**There is no `enable`.** A component absent from an environment is simply
not instantiated there. If something required what it provided, that is a
link error naming both — and it should be, because omitting a certificate
issuer really does break everything needing certificates. A component that
genuinely tolerates absence marks its requirement optional (RFC 0001 §6) and
handles the null.

**Environments are instantiations, so they have distinct identities**, which
is what keeps their state apart. RFC 0003 §5 keys a stack on the
instantiation rather than the definition for exactly this reason: dev and
prod each get their own, and one does not plan to destroy the other's
resources.

## 5. Allocation

Subnets, host ports and pinned addresses are scarce resources shared across
a lab. They are **not** resolved by linking. An address plan is a decision,
so it is written where the lab is declared — visible in §3 above, as literal
values on each cluster.

A lab-level check refuses:

- two clusters whose pod or service ranges overlap
- two clusters whose ranges overlap the host network's
- a pinned address outside the range it claims to be in
- two appliances on one host port

Two alternatives are worth refusing explicitly. Making the allocator a
provider whose value differs per consumer would reintroduce the one shape
RFC 0001 §8.1 rules out. Deriving each range from a cluster's own name needs
no coordination at all — and renaming a cluster would then silently move a
running cluster's subnet, which is the instability that ruled out
graph-derived state identity in RFC 0003 §5. A decision written down and
verified beats a derivation that is wrong under rename.

## 6. Why this terminates

Containment plus linking could in principle chase its own tail. Three rules
stop it, and they are obligations on any implementation.

### 6.1 Containment is acyclic

A floe may not contain itself, directly or transitively. The type is
recursive — a floe holds floes, as a directory holds directories — but the
instance graph is a finite tree.

This is where the borrowed model's own limit is informative. Backpack
composes units freely but **forbids cyclic unit dependencies**; there are no
recursive modules. MixML does permit recursive linking and is markedly more
complex for it. Forbidding cycles is not a simplification we are inventing.

### 6.2 A container's provisions may not depend on its contents

Evaluation is stratified, and the strata are what make the fixpoint
converge:

```text
1. a container's settings and provisions      (from its own configuration)
2. its contents' evaluation                    (may read 1)
3. the container's aggregate delivery          (folds 2)
```

A cluster's `kubernetes-cluster` values come from its own settings. Its
members read them. Its total delivery is its own resources plus its members'
bundles. Three layers, no cycle.

Inverting stratum 1 — a cluster whose version is "whatever my members need"
— is a genuine cycle with no fixpoint, and must be refused rather than
diagnosed by timeout.

### 6.3 Cluster facts a manifest needs are settings, not deferred outputs

RFC 0003 §4 forbids a deferred value from reaching a manifest: a manifest is
rendered at build time and there is nothing to interpolate.

A cluster's members render manifests, so every cluster fact they read has to
be known before apply. In practice this is how it already works — you choose
the pod CIDR and the service CIDR, you do not discover them.

Facts that genuinely are discovered, such as an assigned API endpoint, are
deferred and reach a workload the way any deferred value does: through
publication (RFC 0003 §7), as a handle to a materialised object.

## 7. Open questions

1. **Cross-cluster ordering.** A component in one cluster provisioning
   another is an ordinary requirement, so the link graph knows the edge.
   Whether that edge should also constrain the _apply_ order across clusters
   — rather than being satisfied by the second cluster simply not existing
   yet — is undecided.
2. **What a container may read of its contents.** §6.2 forbids provisions
   depending on contents. Derived aggregates over contents (RFC 0001 §8,
   third flow) are stratum 3 and legitimate. The exact boundary is stated
   here as a rule and not yet as a check.
3. **Sibling containers.** Nothing says whether one cluster may read
   another's provisions. Containment implies not, since neither contains the
   other; the consequence for a lab that genuinely spans clusters is not
   worked out.
4. **Where definitions come from.** §3 writes `import ./harbor.nix`. Whether
   floes are distributed, versioned and resolved by something more than a
   path is left to whatever ships them.

## 8. How to evaluate this concept alone

1. A cluster is declared with a provisioner, a version and its ranges, and
   nothing about it is a special case of the floe model.
2. Swapping k3d for a managed cluster changes one instantiation, and no
   member.
3. The same component appears in two clusters with no renaming anywhere.
4. A shared appliance is instantiated once and satisfies every cluster.
5. A component requiring something nothing provides is a link error naming
   both, not a silent null.
6. Three environments differ by settings and by which members exist, from
   one definition.
7. Two environments' state does not collide.
8. An address plan is written down once and a check refuses an overlap.
9. A floe containing itself is refused, not looped on.
10. A cluster whose facts depend on its members is refused, not timed out.
